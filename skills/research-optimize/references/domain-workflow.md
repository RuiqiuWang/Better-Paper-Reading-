# 新领域：先判断优化问题

## 形成领域画像

从实际入口和代表论文/官方实现确认以下问题，保存到课题的性能记录；引用具体版本，不凭任务名字猜计算图。

| 问题 | 对优化决策的影响 |
|---|---|
| 目标是单请求延迟、离线吞吐，还是达到目标质量的训练总耗时？ | 批量预取可能增加首请求延迟；更快的step未必更快收敛 |
| 一个样本、一个batch、一次optimizer更新分别是什么？ | 固定帧/token/点数、有效batch、梯度累积、padding与实际工作量 |
| 哪些模块训练、哪些冻结，是否有时序或跨样本状态？ | 决定缓存边界、并行粒度和能否重排；不能切断梯度或状态 |
| 质量协议是什么？ | 指标、容差、随机性、固定可视化集；性能选型优先开发/验证子集，最终测试集不反复调参 |
| 数据从哪里读，结果必须保存什么？ | 区分存储/解码/转换/传输/计算/通信/评分/写出瓶颈 |
| 有哪些真实资源约束？ | GPU型号/UUID、显存、CPU核预算、RAM/锁页内存、共享内存、存储容量、调度器/锁与其他负载 |

新领域的论文和官方代码用于识别计算结构、输入信息和质量约束。优化参数仍以当前硬件的小测为准。若已有领域参考，只补不一致的部分。

## 小预算的试验方式

- 优先采用用户给出的预算。未指定时，可将总墙钟约10–15分钟、基线加1–3个候选作为初始提案，结合单次成本缩小；这是可调整的工作约定，不是固定门槛。先估算加载/编译/预热成本，不能先启动一个明显超过预算的“短测”。
- 样本覆盖典型和较长/较大形状、不同编码或内容；保存实际ID与顺序。小测可以减少样本数/更新次数，但保留代表性分辨率、时序窗口和实际推理步数。实在无法容纳时明确缩减覆盖范围，不能宣称原工作负载已验证。
- 原路径基线先跑。每个候选尽量只改一类因素，少量重复区分噪声；组合方案可快速验收总收益，但不据此报告单项因果贡献。候选耗时/资源超过上限、数值失败或连续无收益时停止该候选。
- 两卡同时跑不同配置会混入卡差异；收益接近噪声时在同卡交错比较或交换卡位。记录后台负载、频率、缓存冷暖；不清理共享缓存或终止他人任务来制造“干净环境”。
- 优先测最慢阶段和关键依赖。用其时间占比估算可能收益，避免为了几毫秒的传输花掉大部分调优预算。编译/缓存的准备成本除以每次节省时间可估算收支平衡次数，再与正式任务规模比较。

## 从证据选择候选

| 观察 | 首批候选 | 必须区分 |
|---|---|---|
| 计算频繁等数据 | 读取合并、解码/转换并行、有限预取、线程预算 | CPU供给 vs 存储瓶颈；worker不直接提升PCIe带宽 |
| 传输/同步间隙明显 | 批量传输、锁页/异步、减少不必要往返或标量同步 | 主机不阻塞 vs 实际拷贝与计算重叠 |
| 计算占主导 | profiler定位热点；适用的融合、编译、注意力实现、batch调整 | 编译开销、动态形状、质量/有效batch变化 |
| 显存限制规模 | 调整batch、混合精度、激活重计算或分片 | 省显存不等于更快；重计算可能增加时间 |
| 多卡等待明显 | 每rank数据供给、分片平衡、梯度通信与同步边界 | 最慢rank决定进度，不能只看最快卡 |
| 输出/评测占主导 | 有界后台写出、批量评分、合理且协议允许的记录频率 | 异步副本必须一致，所有输出完成才结束计时 |

这些是候选菜单，不是每项都要尝试。PyTorch相关实现先核对[官方调优指南](https://docs.pytorch.org/tutorials/recipes/recipes/tuning_guide.html)和当前安装版本；其他框架查对应官方工具。不以直接套用某版本API替代兼容性检查。

## 正确性与正式运行

保持算法语义的推理优化先对照原入口，比较样本/帧序、预处理、关键中间体与原始输出；确定性路径优先精确一致。允许误差的计算路径须事前写明容差、指标和原因，不能在看到失败后放宽到恰好通过。

训练小测检查有限loss、梯度、参数更新、有效batch、数据顺序/增强种子和保存恢复行为。涉及精度、batch、优化器或数学路径时，小测只能排除明显错误，不能证明长期收敛等价；采用分阶段扩大和固定验证集观测，不将几步loss相近说成质量已证明。

选定配置将工作负载/代码/权重/环境/硬件及输出策略形成可查的适用条件。正式运行绑定该记录；发生显著形状、版本或资源变化时重测受影响阶段。证据未覆盖的部分写清楚，不把缺失计时填为0。
